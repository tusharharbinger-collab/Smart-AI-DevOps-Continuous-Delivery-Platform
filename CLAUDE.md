**The canary ramp is real progressive multi-step delivery, not one fixed jump.** `pipeline-worker`'s `worker.py` registers `rollout_state:{run_id}` in Redis at trigger time with the pipeline's actual parsed `canary_loop.steps` (e.g. 10% → 25% → 50% → 100%, each with real `minSampleSize`/`minDuration`) and its real gates/guardrails — `policy-controller`'s `controller.py` reads the *live* active step into OPA's input instead of hardcoded stand-ins, and after a `HEALTHY` promotion, `rollout_scheduler.py` schedules the next step's reverification (`POST /pipelines/{run_id}/reverify` on pipeline-worker) to fire once that step's own real `minDuration` has elapsed. A step flagged `requiresManualApproval` (the final 100% cutover, by default) pauses and fires `alert_approval_required`; `POST /internal/approvals/{run_id}` (policy-controller) / `POST /api/v1/projects/{id}/runs/{run_id}/approve` (api-gateway, RBAC-gated) re-evaluates the already-`HEALTHY` verdict with an approval signature rather than re-running verification. Once the final step promotes, `actuation_executor.graduate_canary()` (`POST /internal/pipeline-runs/{run_id}/graduate`) does the real Kubernetes work — reads the canary's **live** image off the cluster, patches the baseline Deployment's matching container to it via strategic merge patch, resets the HTTPRoute to 100/0, and idles the canary Deployment to 0 replicas — and only updates `projects.active_production_tag` if that cluster mutation actually succeeded (fail-soft ordering: DB never claims a version is live that isn't). Both `graduate_canary()` and `emergency_rollback()` are idempotent and safe to retry. Manual "Emergency Rollback" in the UI goes through `POST /internal/manual-rollback/{run_id}` into this same real `emergency_rollback()` path.

**The autonomous git-push-triggered update loop is real, live-verified end to end, and is a two-gate design — don't collapse it into one.** `services/api-gateway/src/routers/webhooks_router.py` (`POST /api/v1/webhooks/github`) HMAC-verifies GitHub's `X-Hub-Signature-256`, dedupes on `X-GitHub-Delivery` via `webhook_registry.py` (Redis-backed repo→tenant/project lookup — Postgres RLS makes this a chicken-and-egg problem for a request that doesn't know its tenant yet, so this lookup deliberately never touches Postgres), and a periodic polling loop (`poll_for_missed_webhook_deliveries`, wired into api-gateway's lifespan, `WEBHOOK_POLL_INTERVAL_SECONDS`) catches deliveries GitHub never retried or that arrived while the platform was down. A `passed=False` gate 1 result never touches `pipeline_executions` at all (mirrors `build_preview.py`'s own "never confused for a real run" invariant) and gets an AI-narrated failure explanation instead (`report_gate1_result` → explainability-service's `/stage-failure-rca`).

**Non-obvious traps already fixed once — don't reintroduce them:**
- RLS policies must be declared without `AS RESTRICTIVE` (plain `FOR ALL USING (...)`, i.e. PERMISSIVE). A RESTRICTIVE-only policy with no companion PERMISSIVE policy makes Postgres deny every row to everyone. Similarly, app services must connect via `APP_POSTGRES_DSN` (`app_user`, non-superuser) — the `platform` DSN is a superuser and unconditionally bypasses RLS regardless of `FORCE ROW LEVEL SECURITY`.
- `SET LOCAL` does not accept a bind parameter (`SET LOCAL x = :val` is a Postgres syntax error at execution time) — use `SELECT set_config('x', :val, true)` instead. And route handlers must depend on `get_request_db` (returns `request.state.db`, the session middleware already scoped), never the plain `get_db` — with `NullPool`, a fresh `Depends(get_db)` session is a different physical connection than the one middleware set `app.active_tenant_id` on, so RLS would silently never apply.
- **`pipeline_executions.status` is written once, as `'PENDING'`, at trigger time and never updated again** — the durable final status lives in `execution_state.status` (written by pipeline-worker via `ExecutionStateStore`). Any query that reports a run's status, or aggregates over it (success rates, MTTV), must read `COALESCE(execution_state.status, pipeline_executions.status)` or it will report every finished run as still pending (found live: every project's 7-day success rate showed 0% despite real completed runs).
- The browser's `EventSource` cannot send custom headers, so it cannot carry the `Authorization: Bearer …` token `tenant_context_middleware` requires — any new SSE consumer must stream over `fetch()` instead (see `frontend/src/hooks/useLiveLogs.ts`) and parse frames itself. Relatedly, `sse_starlette` emits CRLF line endings, so frames are separated by `\r\n\r\n`, not `\n\n` — normalize line endings before splitting or the parser buffers forever and never emits a line.
- A pipeline's generated `build` stage must only set `repoCredentialsEnvVar` for a **private** repo — `git_clone.py` correctly hard-fails when that env var is named but unset, so setting it unconditionally breaks every public-repo build. Thread the repo's actual `private` flag through (see `projects_router.py`'s `repo_private` field) rather than always requesting a credential.
- **Every Kubernetes-facing identifier a project generates must be lowercase-slugified** — Kubernetes Deployment/Service/HTTPRoute names and Docker image names all require RFC-1123-lowercase, but nothing stops a user typing a mixed-case project name (`projects_router.py`'s `_k8s_name()` derives the safe slug for `canaryDeployment`/`baselineDeployment`/`service`/`routeName`/`service_name`/default `path_prefix`; `projects.name` itself keeps the original display name). A manually-typed `container_image` is rejected server-side at creation time (422) if it's not already lowercase — don't let it fail deep inside a build stage instead.
- **`baselineDeployment`/`canaryDeployment` fall back to `{spec.name}` if not explicitly declared, and every pipeline-YAML generator suffixes `spec.name` with `-rollout`** — a real onboarded Deployment never carries that suffix, so an undeclared fallback silently 404s on every actuation/cost-tracking call. The correct fallback source is the `canary_loop` config's own `service` field (matching how `route_name` already works); api-gateway's generator now declares `baselineDeployment` explicitly for exactly this reason — don't remove it or add a new generator that omits it.
- **`handle_incoming_verdict`'s `pipeline_policy` parameter must actually be populated by its real caller** — it was silently defaulting to a generic hardcoded policy (with `manualApprovalRequired.beforeStages` defaulting to `[]`, meaning the approval gate could never fire for any real pipeline) because nothing ever threaded the pipeline's actual declared gates through. `worker.py` now carries the real policy in `rollout_state`; if you add a new caller of verdict handling, it must supply the run's real policy, not a default.
- `verification_records`, `audit_ledger`, `approvals`, and `cost_analysis` all need `ON DELETE CASCADE` on their `pipeline_run_id` FK (added in migration `0009`) to match `execution_state`/`stage_logs` — without it, deleting a project that ever produced a real verdict fails with a 500 `ForeignKeyViolationError` instead of cascading cleanly.
- On Windows, this repo's folder name contains an `&` (`Smart AI DevOps & Continuous Delivery Platform`), which breaks npm's `.cmd` shims under cmd.exe-backed shells (`npm run dev`/`npm run build` silently fail or truncate). Call the underlying script directly instead: `node node_modules/vite/bin/vite.js` (dev server), `node node_modules/.bin/tsc -b` (type-check). Plain `docker`/`git`/`kubectl`/`kind`/`python` are unaffected.
- **A pipeline's `test` stage is deliberately optional and non-blocking** — a blank `test_command` skips cleanly (no guessed default), and a failing one is logged and surfaced as a visible `test_warning` (threaded through both the Gate 1 dry-run callback and the onboarding preview UI) but never fails the pipeline. This was a real fix, not the original design: the wizard used to default every project to a hardcoded `pytest tests/` regardless of language, and `run_test_task` always executes inside `pipeline-worker`'s own `python:3.12-slim` container (no Node/Go/etc.), so a wrong-language or environment-mismatched command used to hard-fail the entire pipeline before it ever reached deploy. Don't reintroduce a guessed default or make test failure blocking again — a project's own Dockerfile running its tests as a build layer is the real gate.
- **A project's `container_image` has no safe auto-fill and must be a real ECR URI** (`<account-id>.dkr.ecr.<region>.amazonaws.com/<name>`, lowercase) — the wizard used to default it to `registry.internal/{name}`, a hostname that only resolves inside the local docker-compose network, which made every real AWS ECS deploy retry a DNS lookup forever (`CannotPullContainerError`) and return a 503 with no useful signal at the app layer. `ensure_ecr_repository_exists` (idempotent) now runs automatically in the build stage for any declared ECR-URI image, since unlike most registries ECR does not auto-create a repository on first push.
- In `verification-engine`'s CloudWatch ARN handling, a load balancer ARN has an extra `/app/` segment a target group ARN doesn't (`loadbalancer/app/name/id` vs. `targetgroup/name/id`) — split on `:` to isolate the resource part first, then strip the `loadbalancer/` prefix only for LB ARNs; treating both the same way silently produces a CloudWatch dimension value that matches nothing. Relatedly, a real, present `cloudwatch: {}` config block (which is exactly what every real project's generated YAML emits, since no per-metric query string is needed unlike Prometheus) is falsy in Python — check `is None` / key-presence, not truthiness, or the whole CloudWatch telemetry path silently never fires.
- **A route handler must never call `db.commit()`/`db.rollback()` itself.** `auth/middleware.py` wraps the entire request in one `session.begin()` transaction and commits it automatically when the handler returns (or rolls the whole thing back on any exception) — a mid-handler explicit commit ends that transaction early, and every subsequent `db.execute()` on the same session then fails with `InvalidRequestError: Can't operate on closed transaction` (found live testing `POST /infra-drafts` against real Postgres — a `FakeDB` test double doesn't model transaction semantics, so unit tests passed while the real endpoint 500'd). This is a *different* cause of the identical error message already documented above for `logs_router.py`'s SSE generator — same symptom, two distinct root causes, check which one applies. One accepted consequence: if a later step in a handler fails, an earlier explicit-transaction write within the same request can't be salvaged as a partial/audit row — the whole request rolls back together by design.
- **In `sqlalchemy.text()`, `:param` immediately followed by `:` is never recognized as a bind parameter** — SQLAlchemy's bind-param regex uses a negative lookahead so that Postgres's own `::type` cast syntax can coexist with `:name` params, meaning `:my_param::jsonb` silently leaves `:my_param` as literal text and asyncpg rejects it as a syntax error (not a bind-param error — the failure looks like plain bad SQL). Always wrap the cast target in parens instead: `(:my_param)::jsonb`.
- **A bare `await db.rollback()` inside a handler rolls back the ENTIRE request transaction, not just the statement that failed.** `delete_project` (`projects_router.py`) used to catch an `IntegrityError` from `DELETE FROM pipelines` (thrown when other `pipeline_executions` rows with a NULL `project_id` still reference it) by calling `db.rollback()` and returning HTTP 200 with `"deleted": project_id` — but that rollback silently undid the already-executed `DELETE FROM projects` too, since both statements share one transaction (see the "route handler must never call `db.commit()`/`db.rollback()`" trap above — this endpoint is one of the few legitimate exceptions to that rule, which is exactly what made the bug subtle). Found live: a project "deleted" via the API stayed fully intact in Postgres. Fixed by wrapping just the `pipelines` delete in `async with db.begin_nested():` (a real SQL `SAVEPOINT`) — a caught `IntegrityError` there now only undoes that one statement, and the outer `await db.commit()` still commits the real project deletion. Any future handler that needs a "delete A, best-effort delete B, tolerate B failing" pattern must use `begin_nested()`, never a bare `rollback()`, or it will silently undo A too.
- **The Groq key's plan caps at 8,000 tokens/minute, and one `infra_generator.py` call already uses ~5,000 (`openai/gpt-oss-120b` is a reasoning model — ~2,200 of those are hidden reasoning tokens).** Two quick clicks of "Preview Infrastructure (AI)", or the 2-attempt retry, exhaust the budget within the same 60s window and Groq answers 429. `generate_infra_proposal()` now parses Groq's `"try again in Ns"` hint, backs off (capped at 20s) and retries once, and on any other HTTP error surfaces Groq's real response body — it used to discard it, so every failure read as an undiagnosable generic `400 Bad Request`. Keep that in mind before assuming a Groq failure is a schema bug, and don't add more back-to-back Groq calls to one user action. Rate-limit waits are bounded (3 × ≤15s) and deliberately independent of the 2-attempt correction-retry budget; an edit sends the whole current proposal (~5,900 tokens requested) so a create-then-edit takes ~40s. Also: in edit mode the prompt must let the human's instruction override the archetype-shape restriction, or the model silently returns the proposal unchanged (found live) — an unchanged edit is now rejected.

- **api-gateway's image has no boto3.** Any shared module the gateway imports must stay boto3-free (`shared/provisioning/aws_arn.py` exists for this; a subprocess regression test guards it) or the gateway crashes at startup. Related BYO-AWS rules: `infra_build_state.aws_connection_id` FK is `ON DELETE RESTRICT` (delete drafts before their connection); the ExternalId travels only in request bodies, never URLs or model prompts; asyncpg returns UUID columns as `uuid.UUID`, so `str()` them before validating (found live - a draft row's connection id 404'd as "not found"); a missing/unverified connection is an error, never a silent fallback to the platform's account. `pipeline-worker` pins boto3 1.43.103 because CloudFormation's early-validation failures only reveal their real reason via `DescribeEvents` (absent in 1.34.144). Infra cost is computed from the AWS Price List (`aws_pricing.py`) and infra safety by `policies/infra_guardrails.rego`, both independent of the model's self-reported numbers/checks; the failure-RCA agent (`infra_failure_analyzer.py`) verifies every evidence line verbatim against real events and falls back to rules.

- **`AWS_ALB_BASE_URL` (api-gateway, pipeline-worker, policy-controller) is static and must match the shared ALB's current DNS name** - the ALB's hostname changes every time it is recreated, and `docker-compose.yml`'s default is now deliberately empty so a stale value fails loudly instead of live-URL checks silently targeting a dead host. Set it in `.env` after any ALB creation and recreate those three containers. Also: an *automated* canary step (anything not `requiresManualApproval`, including the 100% step of an auto-graduating pipeline) needs a positive `minDuration` and `minSampleSize` - `schemas.py` rejects zero floors, so `generate_project_pipeline_yaml` may only emit `0s`/`0` for a human-gated final step. `verify_live_url` treats any status under 500 as verified (a 404 passes); only a 5xx or unreachable app triggers blue-green's post-cutover rollback. api-gateway's onboard/deprovision calls to pipeline-worker use 300s timeouts because a first onboarding creates the ALB (2-3 minutes).

## Key design invariants (do not violate these when editing)

1. **No static thresholds.** Every verification decision must come from a statistical test (SPRT, Mann-Whitney, CUSUM, BOCPD, Fisher/Chi-square, Isolation Forest) or a composite score derived from them — never a bare `if metric > X`.
2. **Metric routing is by `category`.** Pipeline YAML metrics declare a `category` (`error_rate`, `latency`, `saturation`, `business_metric`) and `engine.py`'s dispatcher (§6.0) routes purely on that field to the matching test module in `tests_statistical/`.
3. **`verification-engine` is structurally barred from touching Kubernetes.** It has no `kubernetes` dependency and no kubeconfig mount — only `policy-controller` and `pipeline-worker` can actuate cluster changes. Never add a k8s client import to `verification-engine`.
4. **Verdicts are cryptographically signed.** `verification-engine/src/verdict_signer.py` HMAC-SHA256-signs every `ImmutableVerdict` before publishing to Redis; `policy-controller/src/verdict_verifier.py` must verify the signature (and a freshness window) before a verdict is ever handed to OPA. Never let `policy-controller` act on an unverified verdict.
5. **Traffic shifting goes through the HTTPRoute, never the Deployment.** `actuation_executor.py` patches `spec.rules[].backendRefs[].weight` on the Gateway API `HTTPRoute` via JSON Patch — this is what avoids pod restarts. Don't reintroduce replica-count-based traffic shifting for canary weighting.
6. **Multi-tenancy is enforced via Postgres RLS**, keyed on `tenant_id`, set per-request via `SET LOCAL app.active_tenant_id` (see `auth/middleware.py` and `db/schema.sql`). Any new query path must go through a session that sets this context — do not bypass RLS with a superuser connection for app queries.
7. **Sample-size floor is N ≥ 100**, enforced independently in both `confidence.py` (Python) and OPA `minSampleSize` (defense in depth) — don't lower one without the other.
8. **A `Project` wraps a `Pipeline`; it never replaces the pipeline/run model.** `projects.pipeline_id` FKs to an existing `pipelines` row, and a project's rollouts are ordinary `pipeline_executions` rows (tagged with `project_id`). Never add a separate "project run" table or duplicate verdict/audit logic for projects — every consumer of `pipeline_run_id` (verification, audit, actuation) must keep working unchanged for project-triggered runs.

`services/verification-engine/pyproject.toml` sets `pythonpath = ["."]` and `testpaths = ["tests"]`, so tests import via `src.tests_statistical...`, `src.scoring...`, etc. — run pytest from inside that service directory, not the repo root.

`policy-controller` and `pipeline-worker` tests live under their own `tests/` directories (`services/policy-controller/tests/`, `services/pipeline-worker/tests/`) and are plain pytest, not yet wired into a `pyproject.toml`.

Adversarial and e2e tests at the repo root (`tests/adversarial/`, `tests/e2e/`) import across service boundaries (e.g. `from services.policy_controller.src.verdict_verifier import ...`) and are meant to be run from the repo root.

OPA policy tests: `opa test policies/ -v` (requires the `opa` binary — `bin/opa.exe` is vendored on Windows).

On this Windows dev machine `make` and `kind` are **not on PATH** (`kubectl`/`docker` are, via Docker Desktop): call `./bin/kind.exe` directly and run the recipe bodies from the `Makefile` by hand (or `bash scripts/demo/*.sh`, which only need `kubectl`). Kind and Docker Desktop restart cleanly after machine sleep — Envoy Gateway pods showing dozens of restarts with `Exit Code: 0` is that, not a crash. The Kind cluster is `smartcd-local` (context `kind-smartcd-local`).

Docker Compose in Git Bash quirks: `docker compose logs --since <time>` returns nothing here (use `--tail N` and grep), and `docker compose exec` python output is block-buffered when backgrounded. `curl` against the platform needs a JWT: `POST /api/v1/auth/login` with the seeded `demo@acme-corp.test` / `acme-demo-2026`.

**`make migrate` (`alembic upgrade head`) may not apply cleanly against a long-lived dev database** — this repo's `alembic_version` table has been observed holding stale/inconsistent bookkeeping (a single-row table showing more than one "current" revision from earlier manual intervention). If it fails, don't fight the revision graph: migrations `0001`–`0009` are all idempotent (`CREATE TABLE IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, etc.), so applying a migration's SQL directly via `docker compose exec postgres psql -U platform -d platform` is a safe fallback that was used live for `0006`–`0009`. `db/schema.sql` and every migration file must still be kept in sync either way (schema.sql is what initializes a *fresh* database; migrations are what advance an *existing* one).

## Architecture

Five backend services + a Postgres/Redis/OPA/MinIO infra layer + two real deploy targets (Kind-based Kubernetes with Envoy Gateway, and AWS ECS Fargate — see the deploy-target decision above), wired as a progressive-delivery pipeline:

- **`services/pipeline-worker`** (spec names Celery; actually plain sync function calls + a Redis Streams consumer group, see Phase 5) — parses the declarative pipeline YAML (`pipelines/*.yaml`) into a DAG (`pipeline/dag_builder.py`), executes stages against the real Kind cluster, and persists execution state to both Redis (fast path) and Postgres (durable, resume-after-crash source of truth, via `src/db.py` + `pipeline/execution_state.py`). `worker.py` also registers `rollout_state:{run_id}` in Redis at trigger time (parsed canary-loop steps + the pipeline's real gates/policy) that `policy-controller` reads to drive progressive stepping, and exposes `POST /pipelines/{run_id}/reverify` for policy-controller to call once a step's dwell time has elapsed. `pipeline/reconciler.py` runs on worker startup AND on a periodic loop to resume any pipeline left `RUNNING` when a worker died, from the exact stage it was on. Per-(tenant, service) Redis locks prevent concurrent pipelines racing on the same HTTPRoute.
- **`services/verification-engine`** (Python 3.11, isolated) — `engine.py` dispatches each pipeline metric to a statistical test module under `tests_statistical/` based on the metric's `category`. Produces an `ImmutableVerdict` (`verdict.py`), signs it (`verdict_signer.py`), and XADDs it to `stream:verdicts` (`publisher.py`) — Phase 5 replaced the original bare pub/sub `publish()` with a Redis Stream + consumer group here too, for the same reason as the pipeline-trigger queue (a bare pub/sub channel delivers to every subscriber, so 2+ `policy-controller` replicas would each act on the same verdict). This is the only service intentionally denied Kubernetes access (see invariant 3).
- **`services/policy-controller`** — verifies incoming verdict signatures (`verdict_verifier.py`), evaluates them against OPA policy (`opa_evaluator.py` calling into `policies/delivery_guardrails.rego`), and — only on an OPA `allow_action=true` — actuates traffic-weight changes via the Kubernetes Gateway API (`actuation_executor.py`) or dispatches alerts (`alert_dispatcher.py`)/audit records (`audit_writer.py`). `rollout_scheduler.py` owns the multi-step ramp: advancing/retrying the current step, scheduling the next reverify, handling manual-approval pause/resume (`POST /internal/approvals/{run_id}`), graduation (`POST /internal/pipeline-runs/{run_id}/graduate`), and manual rollback (`POST /internal/manual-rollback/{run_id}`).
- **`services/api-gateway`** (FastAPI) — the external API surface: pipeline/project/verification/actuation/policy/reports/audit/github/webhooks/health routers, WebSocket + SSE (live logs), Postgres session management with tenant-scoped RLS (`db/session.py`, `auth/middleware.py`). `routers/projects_router.py` is the Phase 8 project layer (wraps pipelines, generates their YAML from the wizard payload); `routers/github_router.py` is the OAuth flow; `routers/webhooks_router.py` + `webhook_registry.py` are the autonomous git-push trigger described above.
- **`shared/aws_ecs_actuation.py`** — the AWS ECS Fargate analog of `actuation_executor.py`/`cost_tracker.py`: task-definition registration, service creation, weighted ALB target-group traffic shifting, and the ECS-specific cost-tracking helpers `cost_tracker_ecs.py` (policy-controller) reads from.
- **`services/explainability-service`** — builds exact-citation grounded explanations from verdict evidence and calls Groq (`llama-3.3-70b-versatile` by default, via `GROQ_API_KEY`) for root-cause-analysis reports and digests, within a 30s budget with a fallback path.
- **`frontend`** (React + TS + Vite) — one authenticated console at `/projects`: an overview grid (`pages/ProjectsOverview.tsx`), a 3-step creation wizard (`pages/NewProject.tsx`, with GitHub OAuth repo selection), and a per-project workspace (`pages/ProjectWorkspace.tsx`) hosting four tab screens — Pipeline View, Verification Inspector, Policy & Gates, Audit Ledger — via nested routes at `/projects/:id/{pipeline,verification,policy,audit}`. Those four screens are ordinary components reading `{pipelineId, pipelineRunId, tenantId, projectId}` from router outlet context (`types/app-context.ts`, `hooks/useAppContext.ts`) — they have no project-specific variants, which is what lets the same screens serve both a project workspace and (historically) the retired classic console.
- **`policies/delivery_guardrails.rego`** — the single OPA policy gating every actuation: freeze windows, minimum confidence/sample size, manual-approval-required stages, cost-delta ceiling, and right-sizing auto-apply rules. `policies/tests/guardrails_test.rego` covers it.
- **`k8s/`** — Kind cluster config, Envoy Gateway `HTTPRoute`/`GatewayClass` for the payments-service traffic split, and baseline/canary `Deployment` manifests.
- **`shared/logging_config.py`** — structured JSON logging module imported by every service (mounted read-only into each container).

Statistical test responsibilities (all under `services/verification-engine/src/tests_statistical/`):
| category | test | file |
|---|---|---|
| error_rate | Wald SPRT (Bernoulli log-likelihood) | `wald_sprt.py` |
| latency | Mann-Whitney U (+ KS as secondary) | `mann_whitney.py`, `kolmogorov_smirnov.py` |
| saturation | CUSUM + BOCPD (custom NumPy, not `ruptures`) | `cusum.py`, `bocpd.py` |
| business_metric | Fisher's exact / Chi-square (auto-selected by expected cell counts) | `business_metric_test.py` |
| (cross-metric) | Isolation Forest multi-metric anomaly score | `isolation_forest.py` |

`scoring/confidence.py` combines sample sufficiency, variance stability, and elapsed-time stability into a single `C ∈ [0,1]`; `scoring/composite_scorer.py`-equivalent logic weights non-critical metrics into a composite score, while any critical-tier breach or business-metric regression is an immediate hard `FAILED` regardless of the composite.

# Phase 9: Universal Delivery Platform — bring any repo, build it, test it, deploy it anywhere, keep it running

This is the biggest single initiative on the roadmap — effectively its own mini-roadmap. Read this whole file before starting any sub-phase; the sub-phases build on each other in the stated order.

## The vision, stated plainly

A user brings a GitHub repo. The platform builds it, tests it, and deploys it — with the human confirming each step and seeing exactly what's happening and why, at every stage, on its own dedicated page. That whole cycle (build config → test config → deploy config, human-confirmed) happens **once**, to establish the "base model" — the first real, live, running version. Every version after that is **fully autonomous**: push to GitHub, the platform builds the new version, tests it in isolation, and only if it passes does it cut over — old version terminated immediately, new version now serving 100% of real traffic. If anything goes wrong before or after cutover, it rolls back to the last known-good version immediately, automatically, no human needed. The platform can deploy that cycle onto Kubernetes, AWS ECS, Render, Vercel, Railway, or Azure — the human picks the target once, the mechanism adapts.

This is Render's own production deploy mechanism (confirmed via their docs — see Phase 9.4), generalized to any deploy target instead of just Render's own infrastructure, with our own real statistical verification standing in for "trust me, it's fine."

## Why this is a separate phase from everything before it

Phases 1–8 built a real, working *canary* platform — progressive traffic-weight shifting, verified by real statistics, on Kubernetes only, configured through one combined wizard. This phase adds three things that don't exist yet at all: (1) a **second deployment strategy** (blue-green: full cutover + old-instance termination, not a weighted split), (2) a **deployment-target abstraction** (Kubernetes stops being the only place this can run), and (3) a **fundamentally different UX** (per-stage pages with maximum transparency, plus the Reports/Cost visibility that already has backend support but no UI). None of that can be bolted onto the existing single-wizard, Kubernetes-only, canary-only code without first deciding the shape of each — hence a dedicated phase, not a patch to Phase 8.

## Research this phase is built on

- **Harness** (their own docs): pipelines are `Pipeline → Stage → Step`. Core concepts — **Service** (what's deployed), **Environment** (where — staging/prod), **Infrastructure definition** (the specific cluster/namespace/target within an environment), **Triggers**, **Approval steps**. Their Verify step feeds APM metrics to an AI-assisted rollback decision. Our own architecture already matches this shape (pipeline/stages, namespace-as-environment, real statistics instead of APM+AI-guess) — this phase's job is to generalize "Infrastructure definition" so it can mean an ECS cluster or a Render service, not only a Kubernetes namespace.
- **Render** (their own docs/blog): confirmed zero-downtime deploy mechanism — new instance starts, health-checked (via a configured health-check path or "is it listening on its port"), traffic only switches once ready, old instance gets SIGTERM after 60s then SIGKILL if needed. **If any step fails, the deploy halts and the service keeps running the last successful version, automatically.** This is precisely the blue-green cycle in the vision above — proven, not novel.
- **AWS blue-green on ECS Fargate** (multiple reference architectures): ALB + two target groups + CodeDeploy for the cutover. The cost-critical detail: **the standby environment stays scaled down until an actual deployment is happening** — you don't run two full-price environments permanently. This is the answer to building blue-green on a $100 total AWS budget.
- **Existing build system** (this repo, audited live tonight): the deterministic scanner (`shared/repo_scanner.py`), Dockerfile synthesis for Python/Node/Go (`dockerfile_synthesis.py`), and the build-only dry run (`build_preview.py`) are real, tested, and live-verified against a real GitHub repo both ways (Dockerfile present, and synthesized). This is the foundation Phase 9.1 builds the per-stage UI on top of — the backend guarantee already exists, it just isn't exposed as the described step-by-step experience yet.
- **Automated Canary Analysis — validated against production tooling, not assumed:** the "test pass + statistically better/no-worse, else tell the human what to fix" gate (sub-phase 9.6) is a named, established pattern — Google/Netflix's own **Kayenta** (Spinnaker's canary engine) scores each metric pass/fail against a baseline and "can automatically promote or fail the canary, or trigger a human approval path" — a three-way branch matching our own `HEALTHY`/`DEGRADED`/`FAILED`/`UNVERIFIABLE` verdict exactly. **Argo Rollouts** and **Flagger** confirm the same shape in the Kubernetes-native world, and both surfaced a specific, real failure mode worth guarding against deliberately: analyzing metrics against a freshly-deployed version with near-zero real traffic returns null/meaningless data that naive systems misread as failure — this is exactly why our `minSampleSize`/`minDuration` floors and the first-deployment special case (9.3) exist, and this sub-phase must lean on them rather than re-deciding the question. Flagger's docs also independently confirm never gating on hardcoded thresholds, using real traffic metrics over synthetic checks, and Slack/webhook alerting on both promotion and rollback — all already this platform's existing, tested behavior, not new work.
- **GitHub webhook delivery — real constraints, not idealized:** GitHub's own docs confirm delivery is **at-least-once** (duplicates happen), **not auto-retried** beyond GitHub's own attempts once those are exhausted, and a receiver must ack within 10 seconds. This directly shapes 9.6's webhook deliverable: fast-ack-then-process-async (already this platform's pattern via Redis Streams), dedupe on the `X-GitHub-Delivery` header, and a polling fallback as a safety net — not optional hardening, a documented real gap in the delivery guarantee itself.

## Non-negotiable UX principle for every sub-phase below

**Maximum transparency at every step.** Each stage (build, test, deploy, and later blue-green cutover) gets its own dedicated view showing: what the platform is doing right now, what it found/decided and why, what the human needs to confirm or fix, and — on failure — exactly what broke, where, and how to fix it (the human-side vs. platform-side distinction already built into `build_preview.py` is the model to extend everywhere). No stage should ever leave the human staring at a spinner with no explanation, the way the pre-fix onboarding wizard used to.

## Sub-phase 9.4 — Blue-green as a real, distinct deployment mode

**Goal:** A second deployment strategy, alongside the existing canary: new version fully built and tested in isolation, then a hard cutover (100% traffic switches at once, old version terminated immediately) instead of a gradual weighted ramp — matching Render's own proven mechanism.

**Why now, and why this is genuinely new work:** Everything built so far (Gateway API `HTTPRoute` weights, `update_traffic_weights`) is canary-shaped — a gradual split. Blue-green is a different actuation model: bring up the new version fully, health-check it, atomically switch 100% of traffic, then tear down the old one. This needs its own actuation function, its own OPA rule (mirroring how `FIRST_DEPLOYMENT` got its own rule rather than overloading `PROMOTE_STEP`), and its own rollback path (Render's proven behavior: any failure before cutover just discards the new instance and changes nothing; a failure *after* cutover means bringing the just-terminated old version back, which is the harder, more safety-critical case — deserves its own adversarial test the way guardrail bypass already gets one).

**Deliverables:**
- [ ] New `requestedAction: "BLUE_GREEN_CUTOVER"` OPA rule (freeze windows still apply, same principle as `FIRST_DEPLOYMENT`)
- [ ] New actuation function: bring up "green" fully, health-check, atomic switch (Kubernetes: Service selector swap or a 100/0↔0/100 HTTPRoute flip in one patch, not a ramp), then scale "blue" to zero — mirrors `graduate_canary()`'s existing pattern of "only update the DB after the cluster mutation actually succeeded"
- [ ] Immediate-rollback path if the new version fails health checks post-cutover: bring the just-scaled-down old version back up, re-point traffic, before reporting failure — this is the "if new face any problem after deployment we rollback immediately" requirement, and needs a live-verified drill (kill the new version on purpose, confirm the old one comes back and serves real traffic) before it's trusted
- [ ] UI: a dedicated cutover view showing the health-check-in-progress, the atomic-switch moment, and old-instance termination — same transparency bar as every other stage

**Acceptance criteria:** Live-verified against a real cluster: a genuinely bad new version gets caught before cutover (zero real user impact) AND a new version that fails only after cutover triggers a real, confirmed rollback to the old version, not just a log line saying it should have.

**Depends on:** 9.2 (deploy page needs a mode selector: canary vs. blue-green), 9.3 (there must be a base model to update).

## Sub-phase 9.5 — Deployment-target abstraction (deploy anywhere)

**Goal:** Kubernetes stops being the only place this platform can deploy to. A `DeploymentTarget` interface (`deploy()`, `shift_traffic()` or `cutover()`, `rollback()`, `read_cost_metrics()`) with Kubernetes as the first of several real implementations.

**Why last of the "core mechanism" sub-phases:** Every actuation function written in 9.4 should be written *against* this interface from the start rather than adapted to it afterward — but the interface itself can't be finalized until blue-green's real requirements (9.4) are known, since blue-green and canary need different methods on it.

## Sub-phase 9.6 — The continuous update loop ("keep this running for new feature updates")

**Goal:** Once a base model is live (9.3) on any target (9.5), a genuine `git push` to the connected repo's branch triggers the full cycle automatically — but **"automatic" is conditional, not blind**: the new version only ever goes live if it (a) actually builds and passes its own tests, and (b) is verified, by real statistics against the currently-live version, to be no worse. If either check fails, nothing gets deployed, and the human is told exactly what needs fixing — never a silent no-op, never a silent bad deploy.

**This is not a new invention — it's "Automated Canary Analysis" (ACA), and it's the same pattern Google/Netflix's Kayenta, Argo Rollouts, and Flagger all use in production.** Confirmed via their own docs (see Research section): Kayenta computes a pass/fail score per metric against a baseline and "can automatically promote or fail the canary, or trigger a human approval path" — a three-way branch, not binary — which is exactly our existing `HEALTHY` / `DEGRADED` / `FAILED` / `UNVERIFIABLE` verdict model. **This sub-phase doesn't need a new decision engine — it needs the existing verification engine wired to fire on every `git push`, not only on a human-triggered rollout.**

**The two-gate sequence, precisely:**

1. **Build + test gate** (reuses `build_preview.py`, already built and live-tested): the new commit is built and its own tests run in isolation, exactly like the onboarding-time dry run. **Fail here → no deployment attempt at all**, and the human gets the same human-side/platform-side-classified failure message this already produces today (bad code, missing dependency, wrong test — not vague).
2. **Statistical verification gate** (reuses the existing verification engine unmodified): only if gate 1 passes does the new version actually get deployed into a *comparison* position — a real canary slice (existing mechanism) or a health-checked-but-not-yet-cut-over green environment (blue-green, 9.4) — and compared against the live baseline using the same real statistics (SPRT/Mann-Whitney/CUSUM/Fisher) already built, never a new metric-diffing scheme.
   - Verdict `HEALTHY` (statistically no worse, ideally better) → cutover/promotion proceeds automatically.
   - Verdict `DEGRADED` or `FAILED` → **no cutover** — the new version is discarded (blue-green: never receives real traffic; canary: rolled back), and the human gets the existing grounded RCA (already built) naming the specific metric(s) that regressed and by how much — the same explanation quality a human-triggered rollback already gets, just now firing for an autonomous attempt too.
   - Verdict `UNVERIFIABLE` (not enough evidence yet — e.g. too little traffic) → **do not guess either way.** Real bug pattern confirmed in Argo Rollouts' own field reports: querying metrics against near-zero traffic on a freshly-deployed version returns null/meaningless data that some systems wrongly treat as failure. Our `minSampleSize`/`minDuration` floors (N≥100, an existing hard invariant) already exist specifically to prevent this — this sub-phase must retry/wait, not fail, when evidence is merely insufficient. This is also exactly why the first-deployment special case (9.3) exists: a version with literally nothing to compare against must never be run through this statistical gate at all.

**Deliverables:**
- [ ] A real webhook trigger on the connected GitHub branch. Real reliability constraints, confirmed via GitHub's own docs: GitHub does **not** auto-redeliver a failed webhook beyond its own attempts, delivery is **at-least-once** (duplicates are possible and expected), and it expects a 2xx response within 10 seconds. Concretely: (a) ack fast and process asynchronously — this already matches how pipeline triggers flow through Redis Streams today, no new pattern needed; (b) dedupe on GitHub's `X-GitHub-Delivery` header as an idempotency key, since the same push can legitimately arrive twice; (c) a periodic polling fallback (compare latest known commit SHA vs. the branch HEAD) as a safety net for the case a webhook delivery is dropped and never retried.
- [ ] Gate 1 and Gate 2 above wired into the existing trigger path (`POST /{project_id}/rollout`), not a parallel code path
- [ ] Full transparency maintained: every autonomous run gets the same per-stage visibility as a human-triggered one, including a clear "blocked — here's what to fix" state distinct from "still running" — "autonomous" must never mean "opaque," and a blocked update must never look identical to one still in progress

**Acceptance criteria:** Live-verified with three real pushes: one with a genuinely broken build (blocked at gate 1, clear fix-it message), one that builds fine but is statistically worse than the live version (blocked at gate 2, grounded RCA naming the regression), and one that's genuinely better or equal (deploys automatically, old version terminated/traffic moved per whichever mode is configured).

**Depends on:** 9.3, 9.4, 9.5 all being real for at least one target.
